## 1. Tipagens e integrações com o backend

### 1.1 Estado atual

- Schema OpenAPI gerado existe: `app/api/generated/api-schema.d.ts:1` (~3390 linhas, `auto-generated by openapi-typescript`).
- Quem importa o schema: 8 dos 10 modules em `app/api/modules/` (`auth.ts`, `account-settings.ts`, `dashboard.ts`, `donation-settings.ts`, `pix-keys.ts`, `public-donations.ts`, `wallets.ts`, `withdrawals.ts`) + `app/util/auth.server.ts:2`.
- Nenhum `routes/` ou `components/` importa `api-schema` diretamente — bom isolamento (tipos de domínio fluem via modules).
- Padrão HTTP é axios: `app/api/http/client.ts:1` (`import axios`), `apiUrl = VITE_API_URL || "http://localhost:3000" (:4)`, `axios.create({ baseURL, timeout: 15000 }) (:6-10)`, interceptor `Authorization: Bearer` `(:12-18)`, envelope `fetchApi (:27-52)` que captura tudo e nunca lança.
- Exceções legítimas de `fetch` nativo (2): `app/api/modules/profile.ts:145` (`PUT /profile/photo` multipart, fora do schema/JSON) e `app/components/ui/AudioPlayer.tsx:57` (blob de áudio, não é API).
- Auth server bem separada: `app/util/session.server.ts:1-32` (cookie `auth_token`, `HttpOnly`, `SameSite=Strict`, `Path=/`, `Max-Age=7d`, `Secure` em prod) e `app/util/auth.server.ts:1-38` (`requireValidAuth` valida via `GET /auth/me`).

### 1.2 Problemas encontrados

| # | Problema | Evidência |
|---|----------|-----------|
| 1.1 | `any` no envelope HTTP contamina callbacks | `client.ts:25` (`ApiResponse<T=any>`), `:28` (`{data?:any;error?:any}`), `:33` (`catch(e:any)`); `http/types.d.ts:1,13`; `onResult:(result:any)` em `PixKeysModal.tsx:41`, `PixKeyCreateForm.tsx:79`, `wallet/index.tsx:180`, `widgets/overlay.tsx:111` |
| 1.2 | 3 modules ignoram o schema (100% manual) | `widgets.ts:3-29` (`OverlaySettings/QrCodeSettings/Widget` manual vs `WidgetEntity` em `api-schema.d.ts:2292,2313,2334`); `overlay.ts:1-23` (só `fetchApi<void>`); `profile.ts:32-38` (`UsernameResponse/ProfilePhotoResponse` manual) |
| 1.3 | Endpoint duplicado entre modules | `POST /overlay/test` em `overlay.ts:22` e `widgets.ts:69-70` (`testAlert`) |
| 1.4 | Tipos UI divergem do backend sem contrato explícito | `types/donation.ts:21` adiciona `"expired"` client-side; `types/queue.ts:1-11` sem contraparte no schema; `wallets.ts:13-28` + `withdrawals.ts:30-40` (`WalletPage/PaginationMeta/PaginatedResponse` manuais); `dashboard.ts:105-114` (`HomePageData` agrega 8 entidades) |
| 1.5 | `requireValidAuth` não limpa cookie no `catch` | `auth.server.ts:29` limpa quando `!id`, mas `:33-37` redireciona para `/indisponivel` sem limpar cookie inválido |
| 1.6 | Nova instância axios por chamada + fallback inseguro | `createApiClient(token)` em `client.ts:6` cria `axios.create` a cada uso; fallback `\|\| "http://localhost:3000" (:4)` usa `http` se `VITE_API_URL` faltar em prod |
| 1.7 | `limit` de paginação divergente | `10` em `donations.tsx:28` e `wallet/index.tsx:35` vs `20` em `queue-popout.tsx:18` |

### 1.3 Melhorias recomendadas

- **T1.** Tipar envelope com `unknown` + narrowing (`fetchApi<T>(request: Promise<{data: unknown}>)`, `details?: unknown`) e generificar `useFetcherFeedback<T>` para eliminar `any` dos callbacks.
- **T2.** Unificar dono de `POST /overlay/test` (um module) e derivar `OverlaySettings` de `WidgetEntity` ou documentar o porquê da divergência.
- **T3.** Reutilizar `operations["WithdrawalsController_findAll"]["parameters"]["query"]` (já usado em `withdrawals.ts:7-9`) como padrão para todos os paginados; unificar `limit` default.
- **T4.** Em `requireValidAuth`: limpar cookie também no `catch`; distinguir 401 (→ login) de 5xx (→ indisponível).
- **T5.** Remover fallback `http://localhost` em prod ou forçar `https`; considerar singleton/cache de `axios` + `AbortSignal` em loaders.

| Símbolo | Definição | Usos |

### 3.2 Detalhe por hook

**`useQueueSocket` (`hooks/useQueueSocket.ts:11-38`):**

- Conecta em `io(`${apiUrl}/dashboard`, { auth: { token } }) (:18-20)`, namespace `/dashboard`.
- `useEffect [token] (:15,35)`, guard `if (!token) return (:16)` — conecta no mount, reconecta só se token trocar. Sem lazy sob demanda (aba, visibilidade, painel colapsado).
- Cleanup `disconnect (:32-34)`, mas **sem `socket.off()`** (menos explícito que o hook de history).
- Eventos: `queue_sync (:22)` → `setQueue`; `overlay_status (:26-30)` → `setIsPaused`. Sem `emit join/room` (rooming presumivelmente server-side por token).

**`useDonationHistorySocket` (`hooks/useDonationHistorySocket.ts:67-124`):**

- Mesmo `io(`${apiUrl}/dashboard`, { auth:{token} }) (:95-97)` — **mesmo namespace + token que o anterior → 2 conexões paralelas redundantes**.
- Ponto positivo: `filters/page/limit` via `useRef (:85-90)` para **não reconectar a cada keystroke/página**.
- Cleanup correto: `off(created)+off(updated)+disconnect (:116-120)`.
- `applyHistoryEvent (:21-65)` puro/testável, dedup por `id`, respeita `page===1`, remove item que sai do filtro.

**`useOverlayAlerts` (`hooks/useOverlayAlerts.ts:17-152`) — melhor do repo:**

- `io(`${apiUrl}/overlay`, { query: { token } }) (:87)` — único uso de `/overlay`. Auth **divergente**: `query.token` (público, URL de OBS) vs `auth.token` do dashboard.
- Lazy/visibilidade exemplar: `handleVisibilityChange (:119-127)` — `document.hidden` → `discardCurrent+stopHeartbeat+disconnect`; visível + `disconnected` → `connect`. Motivação documentada (OBS “olhinho”/aba background = offline).
- Heartbeat `HEARTBEAT_INTERVAL_MS=25000 (:15)`, `heartbeat_pulse (:47,49)`, `alert_finished {id} (:31)`, `new_donation/skip/clear/pause_alerts/settings_updated (:98-109)`, `tokenInvalid` em 404 (`:76`), `volumeRef` (`:140-145`).
- Cleanup completo: `removeEventListener+stopHeartbeat+discardCurrent+disconnect+socketRef=null (:131-137)`.

**`useDonationStatus` (polling, não socket):**

- `GET /donations/donation/:id` via `getDonationView`, `resolveStatus` (expirado por `expiredAt`).
- `intervalMs=8000` default, `setTimeout(poll)`; para quando `!==pending`; erro sempre reagenda; `connectionLost` após 5 falhas; sem guard `document.hidden`, sem backoff.

### 3.4 Otimizações recomendadas (sob demanda)

1. **W1 (maior ganho). Unificar os 2 sockets `/dashboard` em 1 singleton compartilhado** — `useQueueSocket.ts:18` vs `useDonationHistorySocket.ts:95` são idênticos. Criar `useDashboardSocket(token)` único (context/refcount) multiplexando `queue_sync/overlay_status/donation:*`. Economiza 50% das conexões; 4→2 com popout aberto.
2. **W2. `off` faltante** — adicionar `socket.off("queue_sync"/"overlay_status")` em `useQueueSocket.ts:32-34` como já faz `useDonationHistorySocket.ts:117-118`.
3. **W3. Lazy connect no dashboard** — hoje conecta no mount sempre que há token. Usar `autoConnect:false` + `connect()` só quando seção live visível/expandida ou `document.visible`; desconectar em `hidden` (copiar `useOverlayAlerts.ts:119-127`). Corta conexões ociosas de quem só consulta histórico.
4. **W4. Trocar polling 8s por socket/SSE** — cada QR aberto = 1 req/8s (`useDonationStatus.ts:14,38,45` + `public-donations.ts:160`). Expor room `donation:{id}` ou SSE. Interim barato: pausar em `hidden`, backoff exponencial, documentar parada em `expired`.
5. **W5. Padronizar auth + opções `io`** — `/overlay` usa `query.token` vs `/dashboard` `auth.token`; unificar em `auth` se o backend permitir; fixar `transports:["websocket"]`, `reconnectionDelayMax`, `timeout` explicitamente.
6. **W6. Evitar `loadSettings` REST redundante** — `useOverlayAlerts.ts:109` refaz `GET getPublicSettings` a cada `settings_updated`; usar payload do evento, GET só fallback.
7. **W7. Coordenar popout + página** — via `BroadcastChannel` ou pausar sockets da página quando `localStorage("popout_open")==="1"`.
8. **Nada a fazer**: `dashboard.tsx` sem socket (correto), `private/widgets/overlay.tsx` sem socket (correto), `useDonationHistorySocket refs:85-90` (manter como padrão).

## 4. Tratamento de erros e exceções

### 4.1 ErrorBoundary — inexistente

- Grep `ErrorBoundary|useRouteError|isRouteErrorResponse` → 0 hits em `app/`.
- `root.tsx:36-43` monta só `ThemeProvider > UnsavedChangesProvider > Outlet`, sem boundary. `routes.ts:1-35` sem `ErrorBoundary/handle`.
- Consequência: qualquer `throw` em loader/action cai no fallback padrão do React Router. UIs de erro são pontuais e inline: `donation-confirmation.tsx:54-66` (`AlertMessage`), `overlay.tsx:29-47` (token), `widgets/overlay.tsx:126-144` (card + `window.location.reload():140`).

### 4.2 `try/catch` inconsistente

**Sem `try` (propaga para boundary inexistente):**

- `wallet/index.tsx:29-54` (loader com 2 awaits), `dashboard.tsx:61-73`, `$username.tsx:19-25` (`Promise.all` — salvo porque `public-donations.ts:99-103,113-123` retorna `null/[]`, mas frágil), `login.tsx:24-65`, `verify-email.tsx:23-37`.

**Com `try` mas só `console.error` + fallback silencioso (usuário vê “vazio” em vez de “erro”):**

- `donations.tsx:43-53`, `queue-popout.tsx:34-45`, `configuracoes/conta.tsx:41-46` (→ `FALLBACK_SETTINGS:28-35`), `widgets/regras.tsx:49-54`, `wallets.ts:57-75` (→ `EMPTY_WALLET_PAGE:30-37` sem dizer qual das 3 chamadas falhou), `useInfiniteHistory.ts:35-55`, `profile.tsx:37-41` (try parcial).

**Silenciosos totais (`.catch(()=>{})`):**

- `useOverlayAlerts.ts:82`, `useOverlayAudio.ts:72,78`; único que sinaliza: `AudioPlayer.tsx:41` (`setHasError`).

### 4.3 `useFetcherFeedback` divergente

- Definição: `hooks/useFetcherFeedback.ts:16-33` (dedup + `onSubmitting` quando `submitting`).
- Correto: `widgets/regras.tsx:132-145`.
- Quebrado: `widgets/overlay.tsx:108-111` (`state:"idle"` literal — `onSubmitting` nunca dispara); `wallet/index.tsx:177-191` (usa `useActionData+navigation.state`, só trata `createWithdrawal`, ignora `createPixKey/deletePixKey:97-134` da mesma action) com duplo canal em `PixKeysModal.tsx:38-43` / `PixKeyCreateForm.tsx:76-81`.
- Falha de loader vira `EmptyState` enganoso: `DonationHistoryList.tsx:44-48`, `WithdrawalHistoryTable.tsx:39-43`.

### 4.4 Validação zod — cliente sim, servidor nem sempre

Cliente com `zodResolver` (bom): `LoginForm.tsx:28`, `register.tsx:34`, `forgot-password.tsx:31`, `reset-password.tsx:36`, `ChangePasswordModal.tsx:43`, `ChangeEmailModal.tsx:57`, `OverlaySettingsForm.tsx:65`, `PixKeyCreateForm.tsx:62`, `WithdrawalModal.tsx:74-75`, `useDonationPayment.ts:58-60`.

Servidor sem zod:

- `wallet/index.tsx:62-95` (`Number(amount)` pode `NaN`, sem schema), `createPixKey:97-115`, `deletePixKey:117-134`.
- `widgets/overlay.tsx:46-60` (`Number(volume)` sem `NaN`/faixa, `overlaySchema` nunca usado).
- `verify-email.tsx:23-37`, `login.tsx:24-65` (sem `safeParse`), `configuracoes/conta.tsx:159-182` (intents 2fa sem `safeParse`).
- Sem `action` (fetch direto, validação só cliente, burlável): `register.tsx:40-50`, `forgot-password.tsx:34-36`, `reset-password.tsx:48-51`.
- `profile.tsx:89-107` valida manual em vez de zod, divergindo de `account-validator.ts`.

### 4.5 Mensagens ao usuário — onde falta

- Só `console.error`, sem toast/alerta: `wallets.ts:74`, `donations.tsx:52`, `queue-popout.tsx:44`, `conta.tsx:45`, `regras.tsx:53`, `useInfiniteHistory.ts:55`.
- `connectionLost` ignorado pelos consumidores (`donation-confirmation.tsx:46`, `useDonationPayment.ts:53`) — usuário com rede caída nunca vê “conexão perdida”.
- Moderação via `message.includes("Mensagem não permitida")` (`useDonationPayment.ts:25-27,91-95`) — frágil a mudança de texto do backend; usar `code`.

### 4.6 Melhorias recomendadas

- **E1.** ErrorBoundary global + por layout (privado/público) com fallback no padrão visual (card 26px, pill de retry).
- **E2.** `try/catch` em todos os loaders com UI de erro dedicada (não reutilizar `EmptyState` de “vazio”); `wallets.getWalletPage` deve sinalizar qual fonte falhou.
- **E3.** Corrigir `useFetcherFeedback` em `widgets/overlay.tsx` e `wallet/index.tsx` (um canal por action).
- **E4.** Validar todo `action` no servidor com os schemas já existentes (`overlaySchema`, `createWithdrawalSchema`, `loginSchema`, `verifyEmailSchema`).
- **E5.** Exibir `connectionLost`; trocar match de string de moderação por `code` do backend.
